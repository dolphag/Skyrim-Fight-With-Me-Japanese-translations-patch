# fwm_scan_flag の指摘の調査(FWM 0.3.0 / パッチ 0.3.0-2 時点の翻訳表)

調査日 2026-10-25。元 DLL の SHA-256 は `a2ea3783…ad86`。結果: **出力 20 行(既知 1 + 新規 19)すべて実害なし(誤検出または無害)**。翻訳表の修正は不要。
アドレスは 0.3.0 専用。版が変わったらやり直すこと(この表は引き継がない)。

## 見方
`fwm_scan_flag.py` は「長さ即値(`mov reg, imm`)を書き換えた後、同じ関数内で同じレジスタに `test/and/or/bt` がある」箇所を全て出す。ヒューリスティックで、経路もレジスタの再定義も見ない。以下は 1 件ずつ手で確認した分類。

## 分類
| 区分 | 件数 | アドレス | 理由 |
|---|---|---|---|
| A. `mov ecx, N` の直後に `call`(確保サイズ) | 9 | 0x94785 0x957d5 0x95936 0xa22ea 0xa24bf 0xad00d 0x1517f5 0x1519b6 0x10305b | ecx は呼び出しの引数で、そこで消費される。後の `and ecx, 0xf` 等は別の値。0x10305b は既知。 |
| B. `mov r8d, N` の直後に `call`(長さ引数) | 3 | 0x10ba6f 0x10ba8d 0x10bd94 | 同上(r8 は呼び出しの引数)。 |
| C. 後で別の値に上書きされる | 3 | 0x119533 (ebx、0x11956a で上書き) / 0xf79c2 (edx、後続で多数回上書き) / 0x1034b1 (eax、0x10353d で上書き) | 書き換えた値が後続のフラグ判定に届かない。 |
| D. クリーンアップ用フラグ兼用だが、判定されるビットが変わらない | 4 | 0xe514d 0xe54d8 0xe5665 (edi 4→6、判定は bit2 と bit3 のみ) / 0x136afd (ebx 4→5、bit0 は判定されない) | 4→6 は bit1 が増えるだけ、4→5 は bit0 が増えるだけ。その関数で `test/bt` されるビットは edi が 4・8、ebx が 2・4・8・0x10・0x20・0x40・bt 8〜12・bl の符号(bit7)で、増えたビットは含まれない。 |
| E. 上書きされる | 1 | 0x137442 (ebx、0x137463 で `mov ebx, 0x80`) | |

(出力は全 20 行。既知の 0x10305b を除く 19 件が今回の調査対象で、表では 0x10305b を A に含めて 20 件を分類している。)

## 副次の確認
`fwm_verify.py` の「旧長さ即値が近傍に残存 0x13c906(被ダメージ)」: 隣の「攻撃速度」の訳が `攻撃速度` = 12 バイトで、元の長さ 12 と偶然一致しているだけ。0x13c906 自体は 12→15 に書き換わっている。実害なし。

## 限界
- 経路を全て追ったわけではない(D の 0x136afd は、判定されるビットの集合から無害と判断した。実機で当該画面を開く確認は未実施)。
- 翻訳を変えて長さが変わると、D の判定ビットとの重なりが変わりうる。D の 4 か所(edi 3、ebx 1)に関わる文字列の長さを変える場合は再確認する。
